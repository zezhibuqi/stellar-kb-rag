# 增强模式与标准模式并存，且复用同一个「当前模型」

系统提供两条问答链路：**标准模式**（意图路由 + 一次权限检索重排 + 一次生成）与**增强模式**（规划拆解子问题 → 并行子答案 → 有界第二轮补充检索 → 逐项合成），由请求级 `mode` 参数选择，前端标注模式名，默认标准模式，同一会话内允许逐条消息混用。增强模式不引入第二个"当前模型"：它复用 `app_settings` 中的当前模型，仅当该提供方在注册表中带 `agent_capable` 标志时可用，否则前端置灰、后端返回 400（`MODE_UNAVAILABLE`）；换用更快的模型由管理员显式切换，系统不会在背后换模型。

**Considered Options**：增强模式作为唯一链路（实现与维护最简，但简单问题也要付多轮调用代价，思考型模型单次调用已达约 15s）；增强模式固定使用 DeepSeek 提供方（速度最优，但等于引入第二个"当前模型"，与 ADR 0006 已否决的 `ROUTER_MODEL` 同构，且 `eval_models.py` 以当前模型名标注报告，背后换模型会污染多模型对比实验）；用原生 function calling 驱动循环（模型侧能力差异大，scnet 端点已实测 `response_format` 异常，再叠一层工具调用能力矩阵风险更高）；会话级锁定模式（切换模式必须新建会话，交互别扭）。

**Consequences**：注册表新增 `agent_capable` 能力标志并在 `/settings` 页面展示，增强模式的可用性随当前模型变化；循环用 JSON 协议驱动（复用 `llm.invoke_json` 的宽容解析与重试），不使用原生工具调用；规划判定为单跳时退化为单次生成，该判定只写入 trace，界面上不做"未拆解"提示；增强模式仅支持流式（`stream=true`），非流式请求返回 400（`MODE_REQUIRES_STREAM`），因为过程事件与 trace 在非流式响应中无处安放；增强模式不改变权限模型——知识检索与订单查询工具的权限固化在工具内部，规划输出一律视为不可信输入；评测报告需同时标注模式与当前模型。
