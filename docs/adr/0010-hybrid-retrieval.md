# 增强模式检索改为双通道（BM25 关键词 + 向量）并引入 RRF 融合与双预算池

**背景（实测）**：探针显示，年报第 26 行的"21万吨…同比增长超六成"与第 136 行的释义表，在纯向量召回的 top-30 里分别是「完全不存在」与「排第 8 但被重排挤掉」；把召回 k 从 10 提到 30、候选数 3 提到 5、重排保留数 9 提到 12 均无效。结论：**字面精确目标需要一条字面检索通道**，调参治不了候选生成层的缺口。

**决策**：增强模式的检索改为两条通道——BM25 关键词通道（SQLite FTS5 + trigram 分词器）与既有向量通道。两路分别取 80 / 50 条后按 RRF 融合（k=60，只用名次、不比较两路分值），融合后截 30 送重排、重排保留 12、工具返回 5。

查询词构造：按标点/空格/数字/单位/英文切分；中文片段 ≤6 字整段作短语词，超过 6 字先整段、零命中再用头/中/尾片段补充；所有词包成双引号并翻倍内部引号。

**关键词席位保护按「最稀有命中词优先」**：融合 + 重排之后为关键词字面命中保留 2 个席位（`AGENT_KEYWORD_RESERVED`），因为释义表这类块语义分低、会被重排整体淘汰，而它是「正式全称」类目标的唯一依据。取席位时按命中词从最稀有到最常见排序后取前几组——按列表顺序取会先取到「年报」这类高频词的命中，等于没有保留。

**MATCH 与 LIKE 是降级关系，不是并行，且降级按词判定**：长度 <3 的词直接走 LIKE；长于 3 字的中文片段仍会派生 2 字头/尾词走 LIKE（「年报释义」在语料里不存在，但「释义」在），因此不能用「整条查询是否命中」来决定是否降级——否则「SC-300」命中就会掩盖「释义」无法字面匹配的事实。LIKE 自带 20 条独立配额，既不占用也不补充关键词通道的 80 条（不参与 RRF）。

**权限**：FTS 行携带 domain，走与向量通道同一套「角色 → 允许领域」过滤；LIKE 路径同样过滤——它是绕过 Chroma 的第二条路，漏掉即越权。

**索引生命周期**：表结构随 `init_db()` 创建；数据由灌库钩子增量维护、`keyword_index.backfill()` 按 `keyword_indexed_at IS NULL` 回填存量（幂等、可重复跑）、删除文档时按 doc_id 清理；索引写入失败不阻塞灌库，但通过 `documents.keyword_indexed_at` 留痕并在健康检查中暴露未入索引的文档数。

**证据单元折叠是双通道之外的第二号根因（成因已于 2026-10-22 更正）**：原判断为「年报转换后没有 Markdown 标题」，实测证伪——清洗前该文件已有 645 个标题（重导出后的当前文件为 653 个标题行）。真正的机制在切片器：`splitter._scan_blocks` 只按「行首是否为 `|`」区分文本块与表格块，标题行与单行 HTML `<table>` 都被归为文本；年报的 288 张表全是 HTML、管道表为 0，于是**整篇文档被并成一个文本块**，而章节归因发生在**块级**（取块内首个非空行之前的最近标题），命中的是全文唯一的 level-1 标题，`_section_end` 找不到同级或更高级标题便返回文档末行——510 个切块因此全部落在同一个「章节」证据单元里。按 `(doc_id, parent_start_line, parent_end_line)` 去重会把整篇折叠成一条候选，同一文档里其余相关块永远进不了上下文。当时的修复放在检索期：证据单元跨度超过 200 行时，去重键退化为切块粒度（`(doc_id, "chunk", chunk_id)`），同一文档内的多个不同块可以同时入选；表与小章节不受影响，原有去重意图保留。这是**权宜之计**：它只解开去重折叠，`chunk_type=table`、整表证据单元与表格前缀对这篇文档依然没有生效。

**根治走的是数据侧（2026-10-22 补记）**：重新导出年报，并把 288 张 HTML 表机械转换为 GFM 管道表（colspan 值置首列、其余列留空；rowspan 值向下传播到被覆盖的每一行，防止财务报表错列；首行作表头并补分隔行；删全空列）。转换后用 `split_markdown` 实测：块数 1→587、distinct 证据单元 1→527、`chunk_type=table` 的块 0→383、最长行 26,268→1,902 字符（按当前重导出文件实测）；重灌后该篇切块数 510→704。**没有改切片器代码**，因此「block 级章节归因」这个缺口仍然存在：任何不含管道表格的文档（纯叙述型，或表格仍以 HTML 落地）都会塌成一个证据单元，检索期的 200 行退化仍是必需的兜底。

**第二轮证据分为两个独立预算池**：链式池与缺口补充池。链式池额度**按需求动态计算**（每子问题配额 × 链式子问题数），`AGENT_CHAIN_EVIDENCE_BUDGET`（15）是安全阀而非固定额度——规划器拆出的子问题数量本身可变，固定池必然在某些轮次饿死排在后面的链式义务；缺口补充池固定 4，因为它是机会性补查。去重集合全局共享（分的是预算不是去重范围），链式池先跑（义务优先，且可能顺带补上缺口），池未用满不借用、余量写入 trace。

**trace 支持变体级归因**：每个子问题下记录 `retrieval.variants[]`（变体类型、查询串、各通道命中数与最佳名次、融合后最佳名次、最终注入条数、是否走 LIKE），顶层记录两个池的用量与限额。

**Considered Options**：只调参数（k / 候选数 / 重排保留）——实测无效，目标块压根不在候选集；用 Chroma 的 `where_document` 子串过滤替代 BM25——需要先有"关键词"，且只能做"限定后按向量排序"，没有 BM25 排序；jieba 等中文分词 + BM25——需新依赖与词表维护，而 trigram 免词典、已验证三字以上可命中（代价是两字以下需 LIKE 兜底）；把关键词通道也接入标准模式与评测主线——会动到已稳定的主链路，先只在增强模式启用、评测加开关按需对照；第二轮沿用单预算池——链式义务会被机会主义的补查抢占，额度不可预测；在切片器层面收窄过大章节、让证据单元天然不折叠——是误诊引出的方案（真正原因不是缺标题，而是切片器不认 HTML 表导致的单块归因），最终由数据侧表格格式转换解决，未动切片器；链式池用固定额度——实现更简单，但规划器多拆一个子问题就会让排在后面的链式义务拿不到证据。

**Consequences**：需要一次本地回填（从 `source_content` 重建切块文本，**不调用 embedding、不需要重灌向量**）；中文两字及以下的词依赖 LIKE 全表扫描，在 865 块规模下可接受，文档量级上去后需重新评估（届时可换分词器或引入词典）；增强模式单次问答的检索开销上升（双通道 + 更宽候选），重排成本由"融合后截 30"约束；检索质量从此可按通道与变体归因，评测需新增"纯向量 vs 混合"对照开关；200 行阈值、席位保留数与两个池的额度都是启发式（够用即可、不是精确参数），若再现"时好时坏"应先看 trace 的 `budgets` 与 `variants` 定位，而不是直接改参数。

**单文档挤占（2026-10-22 年报清洗重灌后新增观测）**：全库规模 671→865 块，其中年报占 704 块（81%）。语义质量变好后，它在**不做权限过滤**的检索评测里吃掉多数 Top-10 席位——实测 3 条掉队的 common 用例，其 Top-10 召回里年报分别占 9、9、6 席，小文档（ESG 纲要 2 块、文化手册 3 块）被挤到召回门外。对照 2026-08-07 基线：finance 93.33%→100%、regulation 86.67%→93.33%、product MRR 0.5889→0.6222，但 common 93.33%→80%，总体 Hit Rate 持平 88%、MRR 0.8322→0.82。两点不要误读：其一，这不等于「清洗无益」——真实用户按角色过滤后，employee 等根本看不到 finance 领域，不存在这种挤占；其二，ADR 0009 已声明 Hit Rate 对块大小不中立，本次同时改变了块的粒度与构成，不能用它给清洗效果下结论。真要治的是检索层的**单文档上限 / 召回多样性**，而不是把数据改回去。
