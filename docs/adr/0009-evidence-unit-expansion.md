# 检索单元与证据单元分离（小块检索、大块证据）

切块（chunk）继续只承担检索与重排的单元职责，尺寸保持 1024 字符级别不放大：bge-reranker-v2-m3 的有效判别区间在 1024 token 附近，块越大向量越趋近"平均脸"、判别力越弱，而增强模式会把检索次数成倍放大，同步放大这个代价。实际注入 LLM 上下文的是**证据单元**——表格为整张表、文本为其所属章节——由切块 metadata 携带的行区间（`parent_start_line` / `parent_end_line` / `parent_type`）定位，命中后从 `documents.source_content` 按行切片展开（ADR 0003 已保证全文存于 SQLite），超长时以命中段为中心向两侧扩展到字符上限。

**Considered Options**：全局放大 `MAX_CHUNK_SIZE`（实现最简，但重排判别力下降、embedding 与 rerank 成本随检索轮数成倍增长）；按文件章节分片、让章节直接成为检索单元（即设计文档 7.1 挂起的方案——块太大，重排失焦）；把"读原文"做成工具交给 LLM 自行决定（灵活，但上下文与步数不可控，已否决）；证据单元不落 metadata、在重排后反查推断（需要额外查询，且无法表达"整张表"这一边界）。

**Consequences**：表格块额外拼接"最近标题 + 表格上方最近的非空非表格行"作为前缀，前缀不计入 `chunk_size` 预算但参与向量化与重排，`start_line` 仍指向表头行、定位语义不变；文本块中，同一章节内被切分出的第 2 段及以后同样补最近标题（第 1 段本就含标题，不重复），因为长章节的后段会丢失章节归属，而只补后段而非全部，是因为给同章节所有块加相同前缀会提高它们彼此的相似度、削弱检索区分度；去重键由 `(doc_id, chunk_id)` 改为 `(doc_id, 证据单元行区间)`，否则同一张表的多个分段会被各自展开、重复注入；切片器改动使已有向量失效，须与源数据重做合并为同一次重灌；设计文档 7.1 的"按文件章节（Heading）分片"待定项就此关闭；评测口径需同步调整——现有 Hit Rate 判定对块大小不中立（块越大越容易包含关键词），不能用它给切片粒度做消融。
